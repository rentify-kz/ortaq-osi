# Анализ спецификации: пробелы и открытые решения

Результат сквозного чтения `docs/spec/`. Каждый пункт — что не описано или противоречит, и предлагаемое решение. Пункты закрываются правкой спецификации.

## Блокируют фазу 0

**1. `User.is_platform_admin` отсутствует в таблице `User`.**
Упомянуто в тексте [02 §4](spec/02-data-model.md#housemembership--роль-пользователя-в-доме), но не в списке полей.
Решение: добавить `is_platform_admin boolean default false`. Выставляется только сидом/CLI, не через API.

**2. RLS + Prisma: механика `SET LOCAL app.current_house_id`.**
`SET LOCAL` действует только внутри транзакции. Prisma по умолчанию не держит запрос в транзакции.
Решение: каждый house-scoped запрос выполняется в `$transaction` через client extension, первой командой `set_config('app.current_house_id', $1, true)`. Два пользователя БД: `app_rw` (под RLS, без `BYPASSRLS`) и `app_admin` (для `/admin/*` и системных задач, отдельный Prisma-клиент). Глобальные таблицы без `house_id` (`User`, `BudgetCategory`, `ReportTemplate`, `LegalDocument`, `LegalChunk`) — без RLS по дому.

**3. «Админка закрыта для мобильного клиента» — клиент нельзя надёжно определить.**
Заголовок клиента подделывается.
Решение: реальная граница — cookie-сессия веба с `SameSite=Strict` + отдельный origin админки; Bearer-токены мобильного клиента для `/admin/*` не принимаются. Формулировку в [03 §4](spec/03-api-contract.md#4-админ-панель) уточнить.

**4. Председатель, живущий в доме.**
Уникальность `HouseMembership (user_id, house_id)` среди активных = одна роль в доме. Председатель почти всегда — собственник этого же дома.
Решение: роль в `HouseMembership` — служебная (`CHAIRMAN`), права жильца (заявки, свои начисления, голос) выводятся из `UnitOwnership`, а не из роли `RESIDENT`. Зафиксировать в 02 и в матрице прав.

## Блокируют фазу 1

**5. Приглашение бухгалтера не описано.**
Роль `ACCOUNTANT` «приглашается председателем по почте» ([00](spec/00-overview.md#роли)), но нет ни flow, ни эндпоинта; `Invite.target_role` = только `RESIDENT | WORKER`.
Решение: `POST /houses/:id/members` с `{role: ACCOUNTANT, email}` → письмо установки пароля + обязательная 2FA, как у председателя. Step-up обязателен.

**6. Step-up биометрией.**
Сервер не может проверить биометрию сам по себе.
Решение: при входе мобильное приложение регистрирует ключ устройства (Secure Enclave / Keystore); биометрия разблокирует ключ, сервер проверяет подпись challenge. До реализации — step-up только паролем/TOTP для email-ролей и OTP для телефонных.

**7. Step-up для ролей с входом по телефону.**
Жилец и работник без пароля и TOTP. Если какое-то их действие потребует step-up — нужен OTP. Сейчас таких эндпоинтов нет; правило зафиксировать.

## Блокируют фазу 4

**8. Тайна голосования от председателя vs схема данных.**
[14 §4](spec/14-compliance-privacy.md#4-приватность-внутри-дома) требует, чтобы председатель не видел, как проголосовал жилец. `Ballot.user_id` + `BallotAnswer` + подписанный документ бюллетеня позволяют это восстановить любому с доступом к БД, а подпись ЭЦП по определению связывает ИИН с содержимым.
Решение: тайна обеспечивается на уровне приложения (API не отдаёт связку «кто → как» никому, включая админа), а не криптографически. Честно сформулировать это в 09 и 14. Криптографическая тайна при ЭЦП-бюллетенях недостижима без отказа от юридической значимости.

**9. Отказ SIGEX в момент голосования.**
Описан общий подход в [08 §8.10](spec/08-flows-system.md#810-отказы-внешних-сервисов), но `ends_at` неизменяем. Нужно правило: что если провайдер лежал последние сутки голосования. Кандидат — только письменный опрос (ст. 43) как запасной путь, без продления.

## Прочее

**10. Секреты вне Yandex Cloud на `local`/CI.** Lockbox — только прод/staging. Для `local` — `.env` с тестовыми ключами HMAC/AES, генерируемыми при первом запуске; CI — фиксированные тестовые ключи.

**11. Номер заявки `Request.number` в доме.** Порядковый номер требует счётчика на дом без гонок: `HouseCounter(house_id, kind, value)` с `UPDATE ... RETURNING` в той же транзакции.

**12. UUIDv7.** PostgreSQL 16 не генерирует v7 нативно (появится в 18). Генерация на стороне приложения (`uuidv7` npm) в Prisma `@default` через extension.

## Предлагаемый порядок старта (фаза 0)

1. Монорепо: pnpm + Turborepo, `apps/api`, `apps/web`, `packages/shared`, `packages/design-tokens`. `apps/worker` и `apps/mobile` — пустые каркасы.
2. `docker-compose` для local: Postgres 16 + pgvector, Redis, MinIO, Mailpit.
3. Prisma-схема фазы 0: `Organization`, `House`, `Unit`, `User`, `HouseMembership`, `Invite`, `JoinRequest`, `Session`, `OtpCode`, `AuditLog`, `IdempotencyKey`, `File`.
4. RLS-миграции + extension скоупа + тест изоляции A→B как шаблон для каждого эндпоинта.
5. `auth`: email+пароль (Argon2id), TOTP, refresh-ротация с `family_id`, step-up.
6. `audit`: хеш-цепочка, роль БД с `INSERT` only.
7. `admin`: организации, дома, генерация помещений, readiness, заведение председателя.
8. `apps/web`: логин + 2FA, админ-панель (3–4 экрана).
9. CI: lint, typecheck, unit, интеграционные с БД, тесты изоляции.
