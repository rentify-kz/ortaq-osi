## Открытые вопросы (закрыть при подключении к Smart Bridge)

**A. Состав ответа ГБД РН.** Возвращает ли сервис номер помещения и площадь в виде, сопоставимом с `Unit.number`, и можно ли сопоставлять по кадастровому номеру здания или РКА. От этого зависит доля автоматических верификаций. Пока `PropertyRegistryProvider` возвращает нормализованную структуру: адрес, кадастровый номер, номер помещения, площадь, доля.

**B. Механизм согласия на запрос в ГБД РН.** Достаточно ли согласия в нашем приложении или требуется подтверждение через eGov (SMS-согласие). Интерфейс допускает оба варианта: шаг согласия — отдельный статус `VerificationSession`.

**C. Подпись договоров ключом юрлица в eGov mobile.** Подтвердить, что сервис QR-подписания принимает ключи юрлиц (председатель от имени ОСИ, подрядчик от имени своей компании). Если нет — для договоров нужен другой канал подписания (NCALayer в вебе), под тем же `SignatureProvider`.

**D. Формат Digital ID.** Протокол обмена (OAuth2/OIDC или собственный), состав атрибутов, срок жизни результата. Влияет только на реализацию `IdentityProvider`.

**E. Площадь из ГБД РН.** Предлагается как значение для пустого `Unit.area` с подтверждением председателем. Если данные надёжны — можно заполнять площади дома массово запросом по зданию (если сервис это позволяет), что ускорит `is_voting_ready`.

## Статус фаз

### Фаза 0 — выполнена (кроме пунктов ниже)

Сделано: монорепо, схема БД фазы 0 с RLS и ролями, журнал аудита с хеш-цепочкой по домам, вход по почте с обязательным TOTP, ротация refresh-токенов, step-up, API и веб админ-панели (организации, дома, генерация помещений, готовность, назначение председателя), первый экран председателя, заглушки Smart Bridge, CI.

Перенесено в фазу 1 — зависят от входа по телефону (OTP), который относится к фазе 1:
- ссылки-приглашения жильцов (таблица `Invite` уже есть);
- заявки на вступление (таблица `JoinRequest` уже есть).

Известные ограничения, которые нужно закрыть до продакшена:
- лимиты запросов хранятся в памяти процесса → перенести в Redis (фаза 1);
- письма уходят внутри транзакции запроса → outbox через очередь `notifications` (фаза 1);
- проверка утёкших паролей — локальный список → k-anonymity API;
- Terraform для Yandex Cloud и Lockbox — не начаты;
- `deepmerge-ts` (high) внутри CLI-конфига Prisma: внешних данных не получает, уйдёт с обновлением Prisma.

## Исходный план фазы 0

1. Монорепо: pnpm + Turborepo, `apps/api`, `apps/web`, `packages/shared`, `packages/design-tokens`. `apps/worker` и `apps/mobile` — пустые каркасы.
2. `docker-compose` для local: Postgres 16 + pgvector, Redis, MinIO, Mailpit.
3. Prisma-схема фазы 0: `Organization`, `House`, `Unit`, `User`, `HouseMembership`, `Invite`, `JoinRequest`, `Session`, `OtpCode`, `AuditLog`, `IdempotencyKey`, `File`, `HouseCounter`.
4. RLS-миграции, роли БД, extension скоупа + тест изоляции A→B как шаблон для каждого эндпоинта.
5. `auth`: email+пароль (Argon2id), TOTP, refresh-ротация с `family_id`, step-up (TOTP).
6. `audit`: хеш-цепочка, роль БД с `INSERT` only.
7. Интерфейсы `SignatureProvider`, `IdentityProvider`, `PropertyRegistryProvider` + mock-реализации.
8. `admin`: организации, дома, генерация помещений, readiness, заведение председателя.
9. `apps/web`: логин + 2FA, админ-панель (3–4 экрана) на отдельном origin.
10. CI: lint, typecheck, unit, интеграционные с БД, тесты изоляции.
