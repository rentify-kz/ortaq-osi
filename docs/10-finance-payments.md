# 10. Финансы, оплаты и отчётность

Финансовый модуль решает две задачи одновременно: даёт жильцам прозрачность, которой им не хватает, и снимает с председателя обязательную отчётность. Обе решаются одним приёмом — **план счетов выводится из официальной формы отчёта**, а не изобретается.

---

## 1. План счетов задан государством

Категории расходов в системе соответствуют **1:1 строкам официальной формы** ежемесячного отчёта по управлению объектом кондоминиума.

### Почему это главное решение модуля

Обычный подход — дать председателю заводить свои категории: «Уборка», «Лифт», «Зарплата». Выглядит удобно, а к 20 числу оборачивается ручным сопоставлением своих категорий со строками официальной формы. Это именно та работа, которую система должна была снять.

Когда `Transaction.category_code` — это код строки формы, отчёт собирается запросом `GROUP BY category_code`. Ничего сопоставлять не нужно.

Второй эффект: дашборд жильца показывает **те же самые цифры**, из которых собран официальный отчёт. Жилец, открывший опубликованный отчёт, увидит те же суммы в тех же строках. Прозрачность становится проверяемой, а не декларативной.

### Структура справочника

Источник — **форма ежемесячного отчёта по управлению объектом кондоминиума**: Приложение 3 к Приказу №163 от 30.03.2020 («Правила принятия решений по управлению объектом кондоминиума», рег. №20247) в редакции Приказа Министра промышленности и строительства РК №380 от 22.09.2025. Справочник наполняется миграцией `20261029100000_phase3_finance`, версия формы — `order-163-ed-380-2025`.

**Балансовые строки (1–5)** — не проводятся, считаются при сборке отчёта: остаток на текущем счёте, остаток на сберегательном счёте, задолженность по взносам на управление, задолженность за парковочные места и кладовки, задолженность по накопительным взносам на капремонт.

**Поступления (6):**

| Код | Наименование | Счёт |
|---|---|---|
| 6.1 | Ежемесячные текущие взносы собственников квартир, нежилых помещений на управление | текущий |
| 6.2 | Ежемесячные текущие взносы собственников парковочных мест, кладовок | текущий |
| 6.3 | Ежемесячные накопительные взносы на капитальный ремонт (сберегательный счёт) | сберегательный |
| 6.4 | Плата за сданное в аренду (найм) общее имущество | текущий |
| 6.5 | Целевые взносы собственников квартир, нежилых помещений, не предусмотренные сметой | оба |
| 6.6 | Целевые взносы собственников парковочных мест, кладовок, не предусмотренные сметой | текущий |
| 6.7 | Иные поступления (добровольные, частные инвестиции) | оба |

**Расходы (7):**

| Код | Наименование | Счёт | Сверх чека или платёжки |
|---|---|---|---|
| 7.1.1 | Оплата труда за ведение бухгалтерского учёта, статистической и налоговой отчётности | текущий | |
| 7.1.2 | Оплата труда за управление объектом кондоминиума | текущий | |
| 7.1.3 | Обязательные платежи в бюджет (налоги, отчисления) | текущий | |
| 7.1.4 | Банковские услуги | оба | |
| 7.1.5 | Расчётно-кассовое обслуживание | оба | |
| 7.1.6 | Содержание офиса (аренда, связь, канцтовары, оргтехника) | текущий | |
| 7.2.1.1–12 | Услуги по договорам субъектам сервисной деятельности (по видам) | текущий | акт работ, получатель |
| 7.3.1–4 | Текущий ремонт общего имущества (кровля, фасад и подвал, инженерные системы, иное) | текущий | дефектный акт, акт работ |
| 7.4 | Коммунальные услуги на содержание общего имущества | текущий | |
| 7.5 | Хозяйственные расходы (инвентарь, оборудование) | текущий | |
| 7.6.1–4 | Капитальный ремонт (крыша, подвал, фасад, иное) | оба | протокол собрания, акт работ |

Строка 7.2.1 в форме перечисляет виды услуг без номеров («за услуги по дератизации…», «…обслуживание лифтов», «иные расходы») и требует наименование исполнителя. В справочнике это подстроки 7.2.1.1–7.2.1.12 с `in_form = false`: операция проводится на вид услуги, а в отчёт строка печатается как в форме — видом услуги и наименованием исполнителя. Подстроки 7.3.x и 7.6.x взяты из формы годового отчёта той же редакции; ежемесячный отчёт сворачивает их в 7.3 и 7.6.

Проводить можно только **конечные** строки; родительские (6, 7, 7.1, 7.2, 7.2.1, 7.3, 7.6) суммируются при сборке. Направление операции следует из раздела: поступление — `IN`, расход — `OUT`.

### Версионирование

Справочник глобальный — он задан государством, и дом не может придумать свою категорию. Приложение его только читает: права на запись у роли приложения отозваны, новая редакция формы — новая миграция и новый `form_version`.

> **Уточнение по источнику.** На этапе проектирования считалось, что Приказ №20247 (2020) отменён Приказом №362 от 12.09.2025. Проверка показала иначе: №362 отменил Приказ №164, а форма отчёта живёт в Приказе №163 (рег. №20247) и действует в редакции №380 от 22.09.2025. Нумерация строк в новой редакции сдвинулась: поступления — раздел 6 (было 5), расходы — раздел 7 (было 6), балансовых строк пять (было четыре).
>
> `ReportTemplate.schema` по-прежнему данные, а не код: следующая смена приказа не должна требовать релиза.

## 2. Счета дома

Два счёта, разделённых по закону:

| Тип | Назначение | Ограничения |
|---|---|---|
| `CURRENT` — текущий | Взносы на содержание, текущие расходы | Обычные операции |
| `SAVINGS` — сберегательный | Накопления на капитальный ремонт | Расходование **только по решению собрания** |

Разделение обязательно: накопления на капремонт по закону лежат на отдельном сберегательном счёте. Со сберегательного счёта проводятся только капремонт (7.6.x) и банковские расходы (7.1.4–7.1.5), а на него поступают только накопительные взносы (6.3), целевые взносы (6.5) и иные поступления (6.7) — это проверяет сервер. К операциям по 7.6.x требуется протокол собрания.

## 3. Транзакции

### Обязательные поля

| Поле | Почему обязательно |
|---|---|
| `category_code` | Без кода транзакция не попадёт в отчёт |
| `amount`, `occurred_on` | Основа расчётов |
| `period` | К какому отчётному месяцу относится — может отличаться от даты операции |
| `description` | Требование: «добавление категории и названия платежа» |
| `idempotency_key` | Защита от двойного проведения |

### Дополнительные требования по категориям

| Категория | Требуется |
|---|---|
| 7.2.1.x Услуги по договорам | Подрядчик из справочника или наименование исполнителя — печатается в отчёте. Акт выполненных работ |
| 7.3.x Текущий ремонт | Дефектный акт и акт выполненных работ |
| 7.6.x Капитальный ремонт | Протокол собрания и акт выполненных работ |
| Любой расход | Чек или платёжное поручение |

Система не блокирует проведение без акта, но помечает транзакцию и выводит предупреждение при генерации отчёта. Блокировка была бы вредна: деньги часто тратятся раньше, чем оформляются документы, и запрет заставил бы вести учёт мимо системы.

### Неизменяемость

Проведённая транзакция **не удаляется и не редактируется**. Ошибка исправляется переводом в `VOIDED` с указанием причины и внесением верной записи.

Это раздражает в моменте, но отчёт, который меняется задним числом без следа, обесценивает всю заявленную прозрачность. Претензии жильцов к ОСИ обычно строятся ровно на этом — «цифры поменялись»; система должна закрывать вопрос, а не воспроизводить его.

Как это устроено:

- **Черновик → проведение.** Бухгалтер вносит операцию черновиком (`DRAFT`), председатель проводит (`CONFIRMED`); председатель может провести свою операцию сразу. Черновик правится, проведённая — нет. Остаток счёта считается только по проведённым.
- **Исправление.** Проведённую операцию председатель аннулирует с причиной (`VOIDED`), верная запись ссылается на неё через `corrects_id`. Жильцы видят обе: аннулирование с причиной — тоже часть прозрачности.
- **Гарантия на уровне базы.** Триггер `transactions_immutable` не даёт изменить проведённую операцию никому, включая владельца базы: разрешён только переход в `VOIDED` без правки остальных полей. У роли приложения отозвано право удалять операции и документы.
- **Идемпотентность.** Клиент генерирует `idempotency_key` один раз на форму. Повтор с тем же телом возвращает уже созданную операцию, с другим — `409 IDEMPOTENCY_CONFLICT`.
- **Документы** прикладываются и после проведения; изъятие документа — мягкое, со step-up и в аудите. Принимаются фото и PDF; PDF перед сохранением проверяет антивирус (в разработке — эвристика без активного содержимого, в продакшене — ClamAV за тем же интерфейсом).

## 4. Начисления

### Генерация

1 числа каждого месяца автоматически:

```
для каждого Unit:
  для каждого активного тарифа:
    MAINTENANCE:    тариф (₸/м²) × площадь помещения
    CAPITAL_REPAIR: тариф (₸/м²) × площадь
    PARKING:        фиксированная сумма за место
```

Взносы на содержание считаются **от площади** — это стандартная практика и следствие того же принципа, что и в голосовании: обязательства пропорциональны доле в общем имуществе.

Защита от дублей — уникальность `(unit_id, period, type)`.

### Целевые взносы

`TARGETED` автоматически не начисляются: они требуют решения собрания. Председатель создаёт их вручную со ссылкой на протокол — система запрашивает `vote_id`.

## 5. Оплата жильцом

Требование: *«платежи для жильца с ссылкой на платеж Kaspi. Возможность добавить чек дабы показать, что вы оплатили (сразу привязывается к номеру, а номер указан по квартирам и поэтому у ОСИ видно будет кто оплатил а кто нет)»*.

### Режим MVP: ссылка + чек

```
Жилец видит начисление
        │
        ▼
«Оплатить через Kaspi» → deeplink с реквизитами и суммой
        │
        ▼
Оплачивает в приложении Kaspi
        │
        ▼
Возвращается → «Загрузить чек» → фото
        │
        ▼
OCR: сумма, дата, получатель, номер транзакции
        │
        ▼
Проверки: дубликат по хешам, external_ref, сверка с начислением
        │
        ▼
PENDING_REVIEW (+ флаги при расхождениях)
        │
        ▼
Председатель или бухгалтер подтверждает
        │
        ▼
Charge → PAID,  Transaction (IN, код 6.1)
        │
        ▼
Видно в дашборде жильцов и в отчёте
```

**Привязка к квартире автоматическая** — через `UnitOwnership` жильца. Это и есть требуемое «сразу привязывается к номеру».

### Защита от подделки чека

Пока нет merchant API, чек — это фотография, которую можно переиспользовать. Три независимых рубежа:

| Рубеж | От чего защищает |
|---|---|
| `content_hash` (SHA-256 файла) | Повторная загрузка того же файла |
| `perceptual_hash` | Тот же чек, пересохранённый, обрезанный или переснятый |
| `external_ref` UNIQUE | Тот же номер транзакции под другое начисление |

При срабатывании любого — статус `FLAGGED` и пометка председателю. **Автоматического отклонения нет**: у чека может быть законное объяснение (один платёж за два месяца), и решение остаётся за человеком.

Подтверждение оплаты требует step-up аутентификации и пишется в аудит.

### Режим с Kaspi Pay merchant API (позже)

Решение пользователя: *«пока что ссылка + чек, но думаю позже стоит заключить договор с API Kaspi»*.

Архитектура к этому готова. При переключении `House.payment_mode = KASPI_API`:

```
Начисление → счёт через merchant API по номеру телефона
        │
        ▼
Жилец оплачивает в Kaspi
        │
        ▼
Webhook о факте оплаты
        │
        ▼
Проверка подписи webhook, идемпотентность, сверка суммы
        │
        ▼
Charge → PAID автоматически
```

Ручной шаг с чеком исчезает, модель данных не меняется: добавляется метод `KASPI_API` и обработчик webhook. Режим переключается **на уровне дома** — одни ОСИ заключат договор с банком, другие нет, и система должна поддерживать оба одновременно.

Требования безопасности webhook: проверка подписи, защита от повторной отправки, сверка суммы с начислением, идемпотентность по `external_ref`.

## 6. Должники

Требование: *«Выявление должников — анализ в конце месяца кто не заплатил»*.

Последний день месяца: начисления с истёкшим сроком переводятся в `OVERDUE`, формируется сводка по помещениям с глубиной долга.

Градация: 1 месяц (напоминание), 2–3 месяца (повторное уведомление), более 3 месяцев (основание для досудебной работы).

### Ограничение доступа

`GET /houses/:id/debtors` доступен **только председателю и бухгалтеру**. Жилец получает `403`. Просмотр пишется в аудит, выгрузка требует step-up.

Жильцы видят только агрегат — процент собираемости.

Это осознанное отступление от буквального прочтения требования «у ОСИ видно будет кто оплатил а кто нет» — оно выполнено, но список не публикуется на весь дом. Полное обоснование — [14-compliance-privacy.md](14-compliance-privacy.md#4-приватность-внутри-дома).

## 7. Отчётность

Требование: *«автоматическая генерация отчета до 20-го числа по шаблону. Туда входят приход и расход средств, с подтверждением (акт выполненных работ), и выполненные работы»*.

### Сроки

| Отчёт | Срок |
|---|---|
| Ежемесячный | до 20 числа следующего месяца |
| Годовой | до 1 апреля следующего года |

Черновик генерируется **15 числа** — пять дней запаса на исправление недостающих документов. Напоминания 18 и 19 числа, если не подписан.

### Сборка

```
1. Выбрать действующий ReportTemplate по effective_from
2. Транзакции периода GROUP BY category_code
3. Разложить по строкам формы
4. Остатки на счетах → строки 1–2
5. Задолженность → строки 3–5
6. Выполненные работы из TaskCompletion (include_in_report)
7. Проверка полноты подтверждающих документов
8. Рендер PDF по шаблону формы
9. Report (DRAFT) + уведомление председателю и бухгалтеру
```

### Проверка полноты

Самая ценная часть автоматизации:

```
⚠ 2 транзакции без подтверждающих документов
   • Текущий ремонт 95 000 ₸ — нет акта выполненных работ
   • Хозрасходы 18 000 ₸ — нет чека
```

Обычно отсутствие акта обнаруживается на собрании или при проверке, когда исправлять нечем. Система показывает это за пять дней до срока — когда ещё можно запросить документ у подрядчика.

### Приложения к отчёту

| Приложение | Источник |
|---|---|
| Чеки и платёжные поручения | `Transaction.receipt_id` |
| Акты выполненных работ, дефектные акты, протоколы | `TransactionDocument` по виду документа |
| Договоры с подрядчиками | `Contractor.contract_file_ids` |
| **Фотоотчёт выполненных работ** | `TaskCompletion.photo_file_ids` с `include_in_report` |
| Протоколы собраний | `Protocol` за период |

Фотоотчёт реализует требование из блока работников: *«Фото можно использовать в отчете»*. Фотографии, снятые работником при выполнении задачи и подтверждённые председателем, автоматически попадают в раздел выполненных работ.

### Подписание и публикация

Официальная форма требует подписей **бухгалтера и председателя** — отсюда роль `ACCOUNTANT` в системе. Обе подписи ставятся ЭЦП через eGov mobile.

После подписания отчёт публикуется всем жильцам. Закон требует представлять отчёт собственникам в общедоступном месте; публикация в приложении с уведомлением выполняет это требование и фиксирует факт публикации с датой.

## 8. Дашборд

Один набор данных, две подачи.

**Жилец видит:** остатки на счетах, поступления и расходы за месяц, процент собираемости, разбивку расходов по категориям с раскрытием до отдельных операций и просмотром чеков.

**Председатель и бухгалтер дополнительно:** черновики и непроведённые транзакции, поимённых должников, сравнение со сметой, динамику по месяцам, экспорт в XLSX.

Совпадение цифр в обеих подачах — не совпадение, а цель: это единственный способ сделать заявление о прозрачности проверяемым.

## 9. Что не входит в MVP

| Отложено | Почему |
|---|---|
| Показания приборов учёта | Отдельный крупный домен, не был в требованиях |
| Пени за просрочку | Требует отдельного правового основания и решения собрания |
| Рассрочка для должников | Усложняет модель начислений; добавляется по запросу |
