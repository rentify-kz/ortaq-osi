# 07. Flows: работник

**Платформа:** только мобильное приложение.

Работник — сантехник, электрик, дворник, уборщица, консьерж. Он пользуется приложением на ходу, часто одной рукой, в подвале без связи, иногда в перчатках. Это накладывает жёсткие ограничения на интерфейс: крупные элементы, минимум ввода текста, работа без сети, никаких таблиц.

Роль намеренно узкая. Работник не видит финансы, не видит других жильцов, не видит заявки, которые ему не назначены. Ему нужны три вещи: что делать сегодня, как отметить выполнение, что происходит в доме.

---

## 7.1 Главный экран работника

Требование: *«Главная страница с поручениями, рутинная работа (например уборка двора, по расписанию — повторяющийся шаблон)»*.

```
┌─────────────────────────────────────┐
│ Сергей П. · сантехник               │
│ ЖК Асыл Арман, блок 3               │
├─────────────────────────────────────┤
│ 🔴 СРОЧНО                           │
│ ┌─────────────────────────────────┐ │
│ │ Перекрыть стояк                 │ │
│ │ Подвал, 3 подъезд               │ │
│ │ до 10:00 · заявка №51           │ │
│ │                    [Взять]      │ │
│ └─────────────────────────────────┘ │
├─────────────────────────────────────┤
│ СЕГОДНЯ                          3  │
│ ┌─────────────────────────────────┐ │
│ │ Замена участка трубы            │ │
│ │ Подвал, 2 подъезд · заявка №47  │ │
│ │ ◐ в работе          📷 нужно    │ │
│ └─────────────────────────────────┘ │
│ ┌─────────────────────────────────┐ │
│ │ Проверить давление в системе    │ │
│ │ 2 подъезд                       │ │
│ │ ○ не начата                     │ │
│ └─────────────────────────────────┘ │
├─────────────────────────────────────┤
│ ПО РАСПИСАНИЮ                       │
│ ┌─────────────────────────────────┐ │
│ │ 🔁 Обход техпомещений           │ │
│ │ каждую пятницу                  │ │
│ │ ○ не начата         📷 нужно    │ │
│ └─────────────────────────────────┘ │
├─────────────────────────────────────┤
│ ДАЛЕЕ НА НЕДЕЛЕ                  2  │
└─────────────────────────────────────┘
```

Порядок блоков: срочное → сегодня → рутина по расписанию → ближайшее. Работник открывает приложение и видит одну задачу, с которой надо начать, а не список из пятнадцати.

Метка `📷 нужно` предупреждает заранее, что задача требует фотофиксации — чтобы работник не ушёл из подвала, не сфотографировав результат, и не возвращался туда второй раз.

Метка `🔁` отличает повторяющуюся задачу от разовой. Это важно психологически: рутина воспринимается иначе, чем поручение.

Эндпоинт: `GET /me/tasks`

## 7.2 Выполнение задачи

Требование: *«Отметить выполнение задачи с фото фиксацией (фото сразу отображается у жителей после подтверждения выполнения председателем)»*.

### Экран задачи

```
← Замена участка трубы

Подвал, 2 подъезд
Заявка №47 · Течь в подвале
Срок: сегодня до 18:00
Приоритет: высокий

── ОПИСАНИЕ ──
Заменить прогнивший участок трубы
холодного водоснабжения. Материалы
закуплены, лежат в подсобке.

── ФОТО ПРОБЛЕМЫ ──
[📷] [📷]     от жильца

        [Начать работу]
```

Фотографии от жильца показываются работнику до выезда — чтобы он взял нужный инструмент сразу.

### Отметка выполнения

```
← Завершить задачу

Фотофиксация обязательна

┌────────┐ ┌────────┐ ┌────────┐
│   📷   │ │   📷   │ │   +    │
│        │ │        │ │ Добавить│
└────────┘ └────────┘ └────────┘

Комментарий
┌─────────────────────────────────┐
│ Заменил 1.5 метра, поставил     │
│ хомуты. Течи нет.               │
└─────────────────────────────────┘

⚠ Фото увидят жильцы после
  подтверждения председателем

        [Отправить]
```

Предупреждение о том, что фото увидят жильцы, показывается **до** отправки. Работник должен понимать, что снимает не для отчётности, а для публичного показа — это меняет качество снимков.

### Что происходит дальше

```
✓ Отправлено на проверку

Председатель подтвердит выполнение.
После этого жильцы увидят результат.

Статус: на проверке
```

Задача переходит в `SUBMITTED`, а не в завершённое. Разделение `SUBMITTED` → `APPROVED` реализует требование буквально: фото попадает жильцам **только после подтверждения председателем**.

Если председатель вернул на доработку — работник получает уведомление с причиной, задача возвращается в `IN_PROGRESS` с сохранением прежних фото.

Эндпоинты: `POST /tasks/:id/start`, `POST /tasks/:id/complete`

## 7.3 Работа без сети

Подвалы, технические этажи и лифтовые шахты — места без связи, и именно там выполняется работа.

| Действие | Офлайн |
|---|---|
| Просмотр списка задач | да, из кэша |
| Просмотр деталей задачи | да, из кэша |
| Начало работы | да, синхронизируется позже |
| Съёмка фото | да, очередь загрузки |
| Отметка выполнения | да, отправляется при появлении сети |

Фотографии складываются в локальную очередь и догружаются в фоне. Работник видит индикатор «2 фото ожидают отправки» и не обязан ничего делать вручную.

Список задач синхронизируется при каждом открытии приложения и по push-уведомлению. Конфликты разрешаются по правилу «сервер главнее» для содержания задачи и «клиент главнее» для отметки выполнения — задачу мог отменить председатель, но факт выполненной работы терять нельзя.

## 7.4 Объявления для персонала

Требование: *«Объявления»* в блоке функций работников.

Работник видит объявления с аудиторией `ALL` (общедомовые — он тоже должен знать об отключении воды) и `STAFF` (только для персонала — график, инструктаж, изменения в работе).

```
Объявления

🔧 ДЛЯ ПЕРСОНАЛА
   Новый график дежурств с 15 сентября
   вчера

🔧 ДЛЯ ПЕРСОНАЛА
   Инструктаж по электробезопасности
   в четверг 14:00
   3 дня назад

📢 ВСЕМ
   Отключение горячей воды 12–14 сентября
   вчера
```

Объявления, адресованные конкретным жильцам, работник не видит.

## 7.5 Повторяющиеся задачи

Требование: *«рутинная работа (например уборка двора, по расписанию — повторяющийся шаблон)»*.

Шаблоны создаёт председатель, работник видит порождённые ими задачи.

Примеры типовых шаблонов:

| Шаблон | Расписание | Фото |
|---|---|---|
| Уборка двора | каждый будний день | нет |
| Влажная уборка подъездов | пн, ср, пт | да |
| Обход техпомещений | каждую пятницу | да |
| Проверка освещения МОП | первый понедельник месяца | нет |
| Уборка снега | ежедневно, декабрь–февраль | да |

Задача создаётся заранее (`lead_time_hours` в шаблоне) — чтобы работник видел её с утра, а не в момент наступления срока.

**Невыполненная повторяющаяся задача не накапливается бесконечно.** Если уборка двора не отмечена три дня подряд, задачи не превращаются в список из трёх — старые закрываются как просроченные, а председатель получает сигнал. Иначе экран работника через месяц станет свалкой, и он перестанет им пользоваться.

## 7.6 Что работник не видит

| Не видит | Почему |
|---|---|
| Финансы дома, бюджет, свою и чужую зарплату | Не нужно для работы; зарплата — конфиденциальна |
| Заявки, не назначенные ему | Снижает шум; заявки соседей — личные данные |
| Список жильцов и их контакты | Связь идёт через председателя |
| Должников | Персональные данные |
| Голосования | Голос принадлежит собственности; работник голосует только если он ещё и собственник в этом доме — тогда у него две роли |
| Отчёты и протоколы | Публикуются жильцам; работник видит их, если он также жилец |

Если работник одновременно является жильцом этого дома — у него два членства (`HouseMembership`), и в приложении появляется переключатель режима. Права не смешиваются: в режиме работника он не видит финансы, в режиме жильца не видит чужие задачи.

## 7.7 Подрядчики

В MVP подрядчик — запись в справочнике без входа в систему. Задачи на подрядчика назначаются, но отмечает их выполнение председатель, получив результат обычным способом (звонок, акт, осмотр).

**Почему отложено.** Дать личный кабинет внешней организации — значит открыть границу системы наружу: отдельный контур аутентификации, ограниченная видимость данных дома, ответственность за действия сотрудников подрядчика. Прежде чем это строить, стоит убедиться, что подрядчики вообще готовы пользоваться системой, а не продолжат работать по телефону. Архитектура к этому готова: `Task.contractor_id` уже существует, добавится роль и ограниченный набор эндпоинтов.
