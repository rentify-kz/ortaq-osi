## 2. Выбор бэкенда и его обоснование

Пользователь оставил выбор бэкенда за нами. Решение — **NestJS + TypeScript, модульный монолит**.

**Почему монолит, а не микросервисы.** Нагрузка этого продукта — десятки-сотни пользователей на дом. Даже тысяча домов не создаёт проблемы, требующей независимого масштабирования частей системы. При этом домен плотно связан: заявка порождает задачу, задача даёт фото, фото попадает в отчёт, отчёт собирается из транзакций, транзакции связаны с голосованием об утверждении расхода. Разрезать это на сервисы — значит завести распределённые транзакции и eventual consistency там, где достаточно одного `BEGIN`. Микросервисы здесь дают только накладные расходы.

**Почему не BaaS (Supabase, Firebase).** Требование разместить БД в Yandex Cloud с сервером в Казахстане исключает управляемые BaaS. Кроме того, значительная часть логики — расчёт кворума, сборка отчёта по официальной форме, оркестрация ИИ — плохо ложится на «тонкий бэкенд».

**Почему TypeScript на бэкенде, а не Python или Go.** Веб и мобильное приложение уже на TypeScript. Общий язык даёт общий пакет типов и zod-схем: контракт API описан один раз и используется на всех трёх концах. Для команды любого размера это экономит больше, чем даёт выигрыш в производительности от Go, который здесь всё равно не нужен.

**Почему NestJS, а не Express/Fastify напрямую.** Готовые модульные границы, DI, guards для RBAC, интерцепторы для аудита, декларативная валидация. В проекте с шестью ролями и жёсткими требованиями к правам доступа структура важнее гибкости.

## 3. Монорепозиторий

```
osi-project/
├── apps/
│   ├── api/                  NestJS
│   │   ├── src/
│   │   │   ├── modules/      доменные модули (см. §4)
│   │   │   ├── common/       guards, interceptors, filters, decorators
│   │   │   ├── infra/        prisma, redis, s3, очереди
│   │   │   └── integrations/ sigex, gemini, kaspi, sms, push
│   │   ├── prisma/
│   │   │   ├── schema.prisma
│   │   │   ├── migrations/
│   │   │   └── seed/         план счетов, тексты законов
│   │   └── test/
│   ├── worker/               фоновые обработчики BullMQ
│   ├── web/                  Vite + React + Tailwind
│   │   └── src/
│   │       ├── app/          роутинг, провайдеры
│   │       ├── features/     по доменам: requests, finance, voting…
│   │       ├── admin/        админ-панель (PLATFORM_ADMIN)
│   │       └── shared/       ui-kit, hooks, api-client
│   └── mobile/               React Native + Expo Router
│       └── src/
│           ├── app/          файловый роутинг
│           ├── features/     те же домены
│           └── shared/
├── packages/
│   ├── shared/               zod-схемы, типы, enum'ы, коды категорий
│   ├── design-tokens/        токены → Tailwind config + RN StyleSheet
│   └── api-client/           типизированный клиент, общий для web и mobile
├── docs/
└── infra/                    Terraform для Yandex Cloud
```

Инструменты: **pnpm workspaces + Turborepo**. Turborepo нужен ради кэширования сборок и запуска задач по графу зависимостей — без него монорепо из шести пакетов пересобирается целиком на каждое изменение.

### Почему `packages/shared` — ключевой пакет

В нём живут zod-схемы запросов и ответов. Бэкенд использует их для валидации входа, фронтенды — для типизации и валидации форм. Это означает, что **изменение контракта ломает сборку клиента на этапе компиляции**, а не в продакшене. Для системы, где ошибка в контракте финансового эндпоинта — это неверные цифры в официальном отчёте, такая страховка окупается сразу.

## 4. Модули API

Каждый модуль — папка с контроллером, сервисом, DTO и тестами. Модули общаются через сервисы, а не через БД напрямую.

| Модуль | Ответственность |

## 5. Фоновые задачи

Отдельный процесс `apps/worker` на BullMQ. Вынесен из API, потому что распознавание чеков и генерация отчётов — операции на десятки секунд, и они не должны занимать воркеры HTTP.

| Очередь | Задачи |
|---|---|
| `ai` | `request.triage`, `receipt.ocr`, `voice.extract`, `proposal.compare`, `summary.weekly` |
| `documents` | `report.generate`, `protocol.generate`, `pdf.render` |
| `notifications` | `notification.dispatch`, `vote.reminder`, `charge.reminder` |
| `finance` | `charges.generate`, `debtors.detect` |
| `maintenance` | `recurring.tasks.spawn`, `invite.cleanup`, `files.gc` |

Расписания (cron) описаны в [08-flows-system.md](08-flows-system.md).

**Правила надёжности очередей:** все задачи идемпотентны (повторный запуск не создаёт дублей), retry с экспоненциальной задержкой, dead-letter очередь с алертом. Задачи, меняющие деньги, дополнительно защищены ключом идемпотентности в БД — очередь может доставить сообщение дважды, а транзакция не должна провестись дважды.

## 6. Инфраструктура: Yandex Cloud, регион `kz1`

| Компонент | Сервис | Примечание |
|---|---|---|
| БД | Managed Service for PostgreSQL 16 | Приватная подсеть, без публичного IP, TLS обязателен. Расширения: `pgvector`, `pgcrypto`, `uuid-ossp` |
| Файлы | Object Storage | Приватные бакеты, presigned URL, версионирование |
| Кэш и очереди | Managed Service for Redis | |
| Приложение | Compute Cloud + Container Registry | Контейнеры, группа с автомасштабированием |
| Балансировщик | Application Load Balancer | Терминация TLS, WAF |
| Секреты | Lockbox | Ключи шифрования, токены интеграций |
| Логи и метрики | Cloud Logging + Monitoring | Логи без ПДн |

> **Проверить на этапе развёртывания.** Часть serverless-компонентов Yandex Cloud недоступна в зоне `kz1`. Архитектура намеренно опирается только на Compute и Managed-сервисы, чтобы не упереться в отсутствие Cloud Functions или serverless-контейнеров. Если на момент реализации serverless в `kz1` появится — это возможность для оптимизации, но не зависимость.

Инфраструктура описывается Terraform в `infra/`. Ручные изменения в консоли запрещены: без этого невозможно воспроизвести окружение и невозможно доказать, где физически лежат данные.

## 7. Окружения

| Окружение | Назначение | Данные |
|---|---|---|
| `local` | Разработка | Docker Compose: Postgres, Redis, MinIO. Сид-данные с фейковыми жильцами |
| `staging` | Приёмка и тестирование интеграций | Тестовый контур SIGEX. **Прод-данные не копируются** |
| `production` | Боевой | `kz1`, полный набор ограничений безопасности |

Прод-данные никогда не попадают в staging и local. Если нужен реалистичный объём — генератор синтетических данных в `prisma/seed`, а не дамп продакшена. Причина простая: дамп с ИИН жильцов на ноутбуке разработчика — это нарушение закона о персональных данных, а не вопрос удобства.

## 8. CI/CD

```
push → lint + typecheck → unit-тесты → интеграционные тесты (с БД)
     → тесты изоляции домов → npm audit + SAST → сборка образов
     → деплой в staging → smoke-тесты → ручное подтверждение → production
```

**Блокирующие проверки:**
- Тесты межарендной изоляции (см. [13-security.md](13-security.md#1-изоляция-домов)) — обязательны для каждого эндпоинта
- Критические уязвимости в зависимостях блокируют сборку
- Миграции проверяются на обратимость

Деплой API — rolling update. Миграции БД применяются отдельным шагом до выката кода и пишутся так, чтобы старая версия приложения продолжала работать (expand/contract): сначала добавляем колонку, потом код её использует, потом удаляем старую. Иначе rolling update ломается в момент, когда половина инстансов на новой схеме, а половина на старой.

## 9. Взаимодействие клиентов с API

**Транспорт:** REST + JSON. GraphQL рассматривался и отклонён: набор экранов фиксирован и заранее известен, гибкость запросов не нужна, а сложность контроля прав на уровне полей — существенная.

**Реалтайм:** WebSocket-шлюз для уведомлений в реальном времени (новая заявка у председателя, смена статуса у жильца). Fallback — polling. Push-уведомления вне приложения: Expo Push для мобильных, Web Push для веба.

**Версионирование:** префикс `/v1`. Мобильное приложение обновляется не мгновенно, поэтому ломающие изменения требуют новой версии эндпоинта и периода параллельной работы.

**Пагинация:** курсорная, лимит по умолчанию 20, максимум 100. Офсетная отклонена — списки заявок и транзакций постоянно пополняются, и офсет даёт пропуски.

## 10. Что специально сделано адаптерами

Четыре интеграции спрятаны за интерфейсами, потому что все четыре могут поменяться:

| Интерфейс | Сейчас | Возможная замена |
|---|---|---|
| `SignatureProvider` | SIGEX | Прямая интеграция с eGov QR после регистрации в Smart Bridge |
| `PaymentProvider` | Kaspi deep link + чек | Kaspi Pay merchant API с webhook |
| `AiProvider` | Gemini | Claude, YandexGPT — при смене требований или лимитов |
| `PushProvider` | Expo Push | FCM/APNs напрямую |

Бизнес-логика работает с интерфейсом и не знает про вендора. Практический смысл: переход на Kaspi Pay merchant API — это новая реализация `PaymentProvider` и переключение флага на доме, а не переписывание модуля платежей. Это прямо заложено в решение пользователя «сначала ссылка, позже договор с API».
