# 09. Голосования и правовая часть

Самый ответственный модуль системы. Ошибка в заявке стоит одного повторного обращения; ошибка в голосовании даёт протокол, который несогласный собственник оспорит в суде — и выиграет, если нарушены кворум, порог, срок уведомления или порядок идентификации.

Поэтому правовые требования здесь встроены в модель данных и проверки, а не описаны в справке.

> **Дисклеймер.** Этот документ фиксирует понимание законодательства на момент проектирования (сентябрь 2026). Перед запуском в продакшен формулировки, пороги и сроки должны быть проверены практикующим юристом по жилищному праву РК. Система спроектирована так, чтобы изменение порогов и форм не требовало переписывания кода.

## 1. Правовая база

| Норма | О чём | Как отражено в системе |
|---|---|---|
| Закон «О жилищных отношениях», **ст. 42** | Общее собрание собственников: созыв, кворум, порядок принятия решений | `Vote.legal_basis = ART_42_MEETING`, расчёт кворума |
| **ст. 43** | Письменный опрос как форма проведения | `ART_43_WRITTEN_SURVEY` |
| **ст. 44** | Голосование через объекты информатизации (электронное) | `ART_44_ELECTRONIC` — основной режим системы |
| Приказ №362 от 12.09.2025 | Формы ежемесячного и годового отчёта | `ReportTemplate` |
| Закон РК №94-V | Персональные данные | [14-compliance-privacy.md](14-compliance-privacy.md) |

**Электронное голосование в ЖКХ Казахстана легализовано с 3 августа 2026 года.** Ключевое условие, зафиксированное в законе: оно допускается **только при обязательной идентификации собственника**. Это прямо определило архитектуру — без верификации личности через ЭЦП модуль голосования юридически бессмыслен.

## 2. Кворум

**Кворум — более 50% собственников, считается пропорционально площади помещений.**

Это самое частое заблуждение при разработке подобных систем: интуитивно кажется, что голосование — это «один человек, один голос». По закону вес голоса пропорционален площади помещения. Собственник 120-метровой квартиры имеет вдвое больший вес, чем собственник 60-метровой.

```
вес помещения = площадь помещения / общая площадь всех помещений

кворум (%) = Σ вес(помещения, подавшие бюллетень) × 100
достигнут, если > 50%
```

### Следствия для системы

1. **`Unit.area` — обязательное поле для голосования.** Пока хотя бы у одного помещения нет площади, `house.is_voting_ready = false`, и создание голосования блокируется (`422 HOUSE_NOT_VOTING_READY`).

   Это прямое следствие того, что админ-панель при создании дома вводит только *количество* квартир. Количество достаточно, чтобы сгенерировать помещения, но недостаточно, чтобы провести голосование.

2. **Вес считается сервером**, никогда не принимается от клиента.

3. **Помещения, исключённые из голосования** (`is_excluded_from_voting`) не входят ни в числитель, ни в знаменатель — это общедомовые помещения, не находящиеся в частной собственности.

4. **Один бюллетень на помещение**, независимо от числа собственников. При долевой собственности голосует назначенный представитель (`UnitOwnership.is_voting_representative`).

## 3. Пороги принятия решений

| Тип решения (`decision_type`) | Порог | Основание |
|---|---|---|
| `ROUTINE` — текущие вопросы | Простое большинство | Обычные решения собрания |
| `CURRENT_REPAIR` — текущий ремонт | Простое большинство | |
| `TARIFF_CHANGE` — изменение тарифа | Простое большинство | |
| `TARGETED_CONTRIBUTION` — целевой взнос | Простое большинство | |
| `CHAIRMAN_ELECTION` — выборы председателя | Простое большинство | |
| `MAJOR_EXPENSE` — крупный расход | **2/3** | Крупные расходы |
| `CAPITAL_REPAIR` — капитальный ремонт | **2/3** | Расходование сберегательного счёта |
| `MANAGEMENT_CHANGE` — смена способа управления | **2/3** | |
| `LIQUIDATION` — ликвидация ОСИ | **2/3** | |
| `COMMON_PROPERTY_DISPOSAL` — распоряжение общим имуществом | **2/3** | |

**Порог выводится из типа решения автоматически** и не выбирается председателем вручную. Председатель не обязан знать, что смена способа управления требует 2/3, а текущий ремонт — простого большинства. Ошибка здесь означает ничтожное решение, обнаруженное через месяцы.

Порог сохраняется в `Vote.threshold` на момент создания — если законодательство изменится, прошедшие голосования сохранят те правила, по которым фактически проводились.

### Расчёт результата

```
Порог считается от суммы весов ПОДАННЫХ бюллетеней,
а не от общей площади дома.

SIMPLE_MAJORITY: голосов «за» > 50% от поданных
TWO_THIRDS:      голосов «за» >= 66.67% от поданных

Голоса «воздержался» входят в знаменатель:
они учитываются в кворуме, но не поддерживают решение.
```

Обработка «воздержался» — неочевидный момент, который стоит согласовать с юристом до запуска. Текущая реализация: воздержавшиеся учитываются в кворуме (они пришли на собрание), но их голос не считается поддержкой. Это консервативный подход — он затрудняет принятие решения, что безопаснее, чем обратное.

## 4. Срок уведомления

**Собственники должны быть уведомлены не позднее чем за 5 календарных дней** до даты голосования, с указанием повестки, формата, даты и места проведения.

Реализация:

```
1. Председатель создаёт голосование (DRAFT)
2. Нажимает «Разослать уведомление»
   → notice_sent_at = now()
   → уведомления всем собственникам
   → статус NOTICE_SENT
3. Поле «Дата начала» ограничено:
   min = notice_sent_at + 5 календарных дней
4. При активации проверяется повторно:
   if (starts_at - notice_sent_at) < 5 дней → 422
```

Проверка стоит дважды — в UI и на сервере — потому что ограничение поля в интерфейсе обходится прямым запросом к API.

Уведомление доставляется по всем доступным каналам (push, SMS для критичных) и фиксируется: кому, когда, каким каналом. Список уведомлённых прикладывается к протоколу — закон требует прикладывать копии уведомлений.

**Рекомендуемый срок — 7 дней.** Разные источники трактуют норму как 5 или 7 дней. Система жёстко блокирует менее 5, но по умолчанию предлагает 7 и показывает подсказку. Это тот случай, когда запас дешевле спора.

## 5. Подписание через SIGEX

### Почему посредник, а не прямая интеграция

Прямое подключение к сервису подписания eGov mobile требует регистрации информационной системы в **Smart Bridge** — государственной интеграционной платформе. Это длительный бюрократический процесс с неопределённым сроком.

SIGEX предоставляет готовый API поверх той же технологии QR-подписания eGov mobile. Юридическая значимость подписи та же — подписывает всё равно сам гражданин своей ЭЦП в приложении eGov mobile; SIGEX только организует обмен данными.

Решение зафиксировано пользователем. Прямая интеграция остаётся возможной позже: обе реализуют один интерфейс `SignatureProvider`.

### Схема подписания

```
Клиент                  Наш API              SIGEX           eGov mobile
  │                        │                   │                  │
  │ POST /ballot/start     │                   │                  │
  ├───────────────────────►│                   │                  │
  │                        │ сформировать      │                  │
  │                        │ документ          │                  │
  │                        │ бюллетеня         │                  │
  │                        ├──────────────────►│                  │
  │                        │  регистрация      │                  │
  │                        │  процедуры        │                  │
  │                        │◄──────────────────┤                  │
  │ QR + deeplink          │   qrId, ссылки    │                  │
  │◄───────────────────────┤                   │                  │
  │                        │                   │                  │
  │ открыть deeplink / отсканировать QR        │                  │
  ├────────────────────────────────────────────────────────────► │
  │                        │                   │  пользователь    │
  │                        │                   │  подписывает ЭЦП │
  │                        │                   │◄─────────────────┤
  │                        │                   │                  │
  │ POST /ballot/complete  │                   │                  │
  ├───────────────────────►│                   │                  │
  │                        │ забрать подпись   │                  │
  │                        ├──────────────────►│                  │
  │                        │◄──────────────────┤                  │
  │                        │                   │                  │
  │                        │ ПРОВЕРИТЬ подпись │                  │
  │                        │ извлечь ИИН, ФИО  │                  │
  │                        │ сверить с реестром│                  │
  │                        │ записать Ballot   │                  │
  │ ✓ голос учтён          │                   │                  │
  │◄───────────────────────┤                   │                  │
```

### Правила, не подлежащие обсуждению

1. **Подпись проверяется на сервере.** Клиент сообщает только «я завершил подписание». Утверждению клиента «подпись валидна» не доверяем — иначе подделка верификации сводится к перехвату одного HTTP-ответа.

2. **Сервер сам забирает подпись у SIGEX** по идентификатору процедуры. Подпись не передаётся через клиента.

3. **ИИН из сертификата сверяется с реестром.** Подпись подтверждает, что документ подписал владелец ЭЦП, но не то, что он собственник этого помещения. Второе устанавливается сверкой с `OwnerRegistryEntry`.

4. **Сохраняется всё:** подпись, цепочка сертификатов, серийный номер, срок действия, метка времени, результат проверки. Через год при разбирательстве этого должно хватить для доказательства.

5. **Ключи SIGEX только на сервере.** Мобильное приложение и веб к SIGEX напрямую не обращаются.

### Назначения подписи

| `purpose` | Что подписывается | Кто |
|---|---|---|
| `IDENTITY_VERIFICATION` | Согласие на обработку ПДн при регистрации | Жилец |
| `BALLOT` | Бюллетень | Собственник |
| `PROTOCOL` | Протокол собрания | Председатель + секретарь |
| `REPORT` | Ежемесячный / годовой отчёт | Председатель + бухгалтер |

Одна интеграция закрывает четыре задачи — в этом её ценность. Та же подпись, что подтверждает личность при регистрации, удовлетворяет требование ст. 44 об обязательной идентификации при голосовании.

## 6. Снимок реестра

**Ключевое решение модуля.** При переходе голосования в `ACTIVE` создаётся `VoteRegistrySnapshot` — замороженная копия реестра:

```json
{
  "total_area": 8420.50,
  "total_units": 128,
  "entries": [
    { "unit_id": "...", "area": 62.40, "owner_user_id": "...", "weight": 0.007410 }
  ]
}
```

Все веса голосов берутся отсюда, а не из текущего состояния таблицы `Unit`.

**Зачем.** Без снимка результат голосования можно переписать, не трогая ни одного бюллетеня: достаточно изменить площади помещений в справочнике после окончания голосования, и пересчёт даст другой итог. Снимок делает результат воспроизводимым: пересчёт через год по сохранённым данным даёт ровно те же цифры, что в протоколе.

Дополнительные следствия:

- Собственник, купивший квартиру во время голосования, в этом голосовании не участвует — на момент старта он не был собственником
- Исправление площади после старта не влияет на идущее голосование, но повлияет на следующее
- Протокол остаётся проверяемым независимо от последующих изменений в доме

## 7. Формирование протокола

Требование: *«автоматическое формирование протокола по окончанию»*.

По закрытии голосования формируется протокол со всем, что требует закон:

```
ПРОТОКОЛ № 5
общего собрания собственников помещений

Объект кондоминиума: г. Алматы, ул. Абая 150
Форма проведения: электронное голосование (ст. 44)
Дата начала: 16 сентября 2026
Дата окончания: 26 сентября 2026

СВЕДЕНИЯ О КВОРУМЕ
Общая площадь помещений: 8 420,50 м²
Приняли участие: 128 помещений, 5 372,28 м²
Кворум: 63,8% — собрание правомочно

ПОВЕСТКА ДНЯ
1. Утверждение замены лифта во 2 подъезде за счёт
   средств капитального ремонта

РЕЗУЛЬТАТЫ ГОЛОСОВАНИЯ
Вопрос 1. Требуемое большинство: 2/3
   За:           71,2%  (3 825,06 м²)
   Против:       22,4%  (1 203,39 м²)
   Воздержался:   6,4%    (343,83 м²)
   РЕШЕНИЕ ПРИНЯТО

ПРИЛОЖЕНИЯ
1. Список участников голосования
2. Уведомление о проведении и список уведомлённых
3. Материалы к повестке
4. Реестр бюллетеней с реквизитами ЭЦП

Председатель: Иванов И.И.        [ЭЦП]
Секретарь:    Петрова А.С.       [ЭЦП]
```

Протокол подписывается ЭЦП председателя и секретаря, публикуется жильцам и хранится **не менее 5 лет** (`retention_until`).

Если кворум не достигнут — формируется протокол о **несостоявшемся** собрании. Система не позволяет «дособрать» голоса после окончания срока: это разрушило бы юридическую значимость всей процедуры.

## 8. Защита целостности голосования

Голосование — единственная часть системы, где ошибка невосстановима: пересчитать нельзя, бюллетени подписаны, решение о миллионах тенге принято.

| Угроза | Защита |
|---|---|
| Двойное голосование от помещения | Уникальное ограничение `(vote_id, unit_id)` на уровне БД |
| Подмена веса голоса клиентом | Вес берётся из снимка на сервере, поле из запроса игнорируется |
| Подделка подписи | Проверка на сервере, клиент результат не сообщает |
| Голосование не-собственником | Проверка `relation = OWNER` + `verification_status = VERIFIED` |
| Изменение результата после закрытия | `Ballot` append-only: у приложения нет прав `UPDATE`/`DELETE` |
| Правка площадей задним числом | Снимок реестра при старте |
| Изменение вопросов после начала | Блокируется после первого поданного бюллетеня |
| Влияние на ход голосования | Промежуточные результаты скрыты по умолчанию |
| Выборочное напоминание «нужным» | Напоминания рассылаются всем непроголосовавшим, вручную адресовать нельзя |
| Продление голосования до нужного итога | Закрытие автоматическое по времени, `ends_at` неизменяем после активации |
| Незаметная правка истории | Все действия в `AuditLog` с хеш-цепочкой |

Подробнее об общей модели угроз — [13-security.md](13-security.md#4-целостность-голосования).

## 9. Письменный опрос (ст. 43)

Альтернативная форма для домов, где часть собственников не пользуется смартфонами.

Отличия от электронного голосования:

- Бюллетени могут заполняться на бумаге, председатель вносит их в систему
- Каждый бумажный бюллетень требует скана как приложения
- Внесение чужого бюллетеня председателем помечается `entered_by_chairman = true` и всегда попадает в аудит
- Смешанный режим допустим: часть собственников голосует электронно, часть на бумаге

**Риск, который нужно понимать.** Возможность вносить чужие бюллетени — это по определению точка, где председатель может злоупотребить. Полностью закрыть её нельзя, не отказавшись от бумажной формы, которая законна и нужна пожилым собственникам. Смягчение: обязательный скан бюллетеня, отметка в протоколе о доле бумажных голосов, доступный жильцам аудит.

Если доля бумажных бюллетеней превышает 30%, протокол содержит явное указание на это.

## 10. Юридический помощник

Требование: *«Юридический помощник по Закону о жилищных отношениях и Правилам, с цитатами статей»*.

### Устройство

RAG по корпусу законодательства: Закон «О жилищных отношениях», Правила содержания общего имущества, профильные приказы.

```
Вопрос председателя
      │
      ▼
Векторный поиск по LegalChunk
(разбиение по статьям, не по абзацам)
      │
      ▼
Топ-5 релевантных статей
      │
      ▼
Gemini: ответ ТОЛЬКО на основе
переданных статей
      │
      ▼
Ответ + точные ссылки на статьи
```

### Правила

1. **Разбиение по статьям, а не по абзацам.** Требование — «с цитатами статей», значит ссылка должна быть точной: «статья 42, пункт 3», а не приблизительный фрагмент текста.

2. **Только на основе найденного.** Если релевантных статей не нашлось — ответ «не нашёл основания в законодательстве, обратитесь к юристу». Юридический ответ без источника хуже отсутствия ответа: председатель на него сошлётся, а он окажется выдуманным.

3. **Обязательный дисклеймер** о том, что помощник не заменяет юридическую консультацию.

4. **Версионирование корпуса.** `LegalDocument.version_date` и `is_current`. При изменении закона старые ответы остаются в истории с указанием, на какой редакции они основаны.

5. **Персональные данные не передаются.** Вопросы касаются права, а не конкретных жильцов; обезличивание применяется на общих основаниях.

### Связка с действием

Ответ помощника заканчивается кнопкой действия там, где это уместно: «Создать голосование по этому вопросу» с уже подставленным типом решения и порогом. Помощник не просто объясняет требование, а ведёт к его выполнению — это снимает главную проблему председателя, который знает, что «надо провести собрание», но не знает как.
