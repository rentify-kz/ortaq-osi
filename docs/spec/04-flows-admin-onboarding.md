# 04. Flows: админ-панель и подключение дома

Это первое, что строится. Без админ-панели в систему физически некого пустить: председатель не может зарегистрироваться сам, а жилец не может попасть в дом, которого нет.

## 1. Карта онбординга

```
Админ платформы                Председатель                 Жилец
──────────────                 ────────────                 ─────
создаёт ОСИ
   │
создаёт ЖК ──────► генерация помещений
   │                     (площади пустые)
связывает ОСИ ↔ ЖК
   │
заводит председателя ──► письмо на почту
                              │
                         задаёт пароль
                         настраивает 2FA
                              │
                         видит свой дом сразу
                              │
                         заполняет площади ──► дом готов
                         загружает реестр       к голосованиям
                              │
                         копирует ссылку
                              │
                         отправляет в чат ЖК ──────► переходит по ссылке
                                                          │
                                                     телефон + OTP
                                                          │
                                                     Digital ID (eGov)
                                                          │
                                                     ГБД РН через Smart Bridge
                                                     (запасной путь — реестр)
                                                       ┌──┴──┐
                                                  найдено    не найдено
                                                       │         │
                                                  VERIFIED   ручное
                                                             подтверждение
                                                             председателем
```

## 2. Flow: создание организации и дома

**Актор:** `PLATFORM_ADMIN` · **Экраны:** админ-панель в вебе

### 2.1 Создание ОСИ

1. Админ открывает `/admin/organizations` → «Создать организацию»
2. Заполняет: наименование, БИН, форма управления (ОСИ или ПТ), юридический адрес, банковские реквизиты
3. Система проверяет БИН на уникальность и формат (12 цифр)
4. Организация создаётся в статусе `ACTIVE`

**Почему БИН обязателен:** он попадает в шапку официального отчёта. Дом без БИН не сможет сформировать отчёт, и обнаружится это только к 20 числу.

### 2.2 Создание ЖК

1. Админ выбирает организацию → «Добавить дом»
2. Заполняет:
   - Адрес (обязательно)
   - Отображаемое имя — то, что увидят жильцы: «ЖК Асыл Арман, блок 3»
   - **Количество подъездов**
   - **Количество квартир**
   - Этажность (опционально)
3. Сохранение → запускается генерация помещений
4. Админ видит превью сгенерированных помещений и может скорректировать разбивку

### 2.3 Генерация помещений

Из «4 подъезда, 128 квартир» система создаёт 128 записей `Unit`: сквозная нумерация 1–128, по 32 на подъезд, этаж вычисляется из этажности.

**Результат редактируемый.** Реальные дома почти никогда не делятся ровно: в первом подъезде бывает 30 квартир, в четвёртом — 34; встречаются номера «12А» и «1/2»; на первых этажах вместо квартир коммерческие помещения. Поэтому генератор — заготовка, а не истина, и админ (или позже председатель) правит результат вручную или загружает точную разбивку по подъездам.

```json
{
  "strategy": "SEQUENTIAL",
  "entrances": [
    { "entrance": 1, "from": 1,  "to": 30, "floors": 9 },
    { "entrance": 2, "from": 31, "to": 64, "floors": 9 }
  ]
}
```

**Ограничение.** Перегенерация блокируется (`409`), если по дому уже есть голосования, начисления или заявки, привязанные к помещениям. Иначе пересоздание `Unit` разорвало бы связи с бюллетенями и платежами — и результаты прошедших голосований перестали бы сходиться.

### 2.4 Что генератор не заполняет: площади

Сгенерированные помещения получают `area = null`. Админ вводит только количество, а площади он не знает — их знает председатель из технического паспорта дома.

**Последствие, заложенное в систему:** пока хотя бы у одного помещения нет площади, `house.is_voting_ready = false`, и создание голосований блокируется на уровне API.

Это не придирка. По ст. 42 Закона «О жилищных отношениях» голоса считаются **пропорционально площади помещения**. Голосование, проведённое без площадей, даёт протокол, который любой несогласный собственник оспорит в суде — и выиграет. Дешевле заблокировать создание голосования, чем объяснять председателю, почему его решение о капремонте на 12 миллионов признано ничтожным.

## 3. Flow: выдача доступа председателю

**Актор:** `PLATFORM_ADMIN` → `CHAIRMAN`

1. Админ на странице дома → «Назначить председателя»
2. Вводит **почту** и ФИО
3. Система создаёт `User` в статусе `PENDING` и `HouseMembership` с ролью `CHAIRMAN`, `joined_via = ADMIN_PROVISION`
4. На почту уходит письмо со ссылкой на установку пароля (токен живёт 72 часа)
5. Председатель переходит, задаёт пароль (минимум 12 символов, проверка по базе утёкших)
6. **Обязательная настройка 2FA** — система не пускает дальше без подключённого TOTP
7. Первый вход → председатель **сразу видит свой дом**. Ни выбора дома, ни ввода кода приглашения

Для подписания протоколов, отчётов и договоров председатель дополнительно проходит Digital ID — ИИН из сертификата ЭЦП при каждой подписи сверяется с подтверждённым. Вход в систему от этого не зависит.

Шаг 6 не пропускается намеренно: председатель распоряжается деньгами дома, и его учётка — самая привлекательная цель в системе. Компрометация почты без 2FA означала бы полный доступ к финансам ОСИ.

**Если ОСИ управляет несколькими домами** — в шапке появляется переключатель. Права проверяются по `HouseMembership` для каждого дома отдельно: председатель одного дома не видит другой, даже внутри той же организации, если членство не выдано.

### 3.1 Восстановление доступа

Председатель забыл пароль → стандартное восстановление по почте. Председатель потерял доступ к почте → только через админа платформы, с записью в аудит и уведомлением на старый адрес. Автоматического пути нет: возможность сменить почту председателя без контроля — это готовый способ захватить управление домом.

## 4. Flow: подготовка дома председателем

**Актор:** `CHAIRMAN` · **Цель:** довести дом до рабочего состояния

При первом входе председатель видит чек-лист готовности вместо пустого дашборда:

```
Подготовка дома                                    3 из 5

✓ Помещения созданы                                    128
✓ Председатель назначен
○ Площади помещений                            120 из 128
○ Реестр собственников                          не загружен
○ Жильцы присоединились                                  0

⚠ Голосования недоступны: у 8 помещений не указана площадь
```

### 4.1 Заполнение площадей

Три пути, по убыванию удобства:

1. **Загрузка реестра собственников** (XLSX/CSV) — площади приходят вместе с ФИО и ИИН. Основной путь для массового заполнения
2. **Массовый ввод** — таблица со всеми помещениями, заполняется с клавиатуры
3. **Поштучно** — при правке отдельного помещения

Площадь, полученная из ГБД РН при верификации собственника, предлагается председателю как значение для пустого `Unit.area` — не записывается автоматически, потому что председатель отвечает за реестр дома.

При заполнении последней площади `is_voting_ready` переключается в `true` триггером, и блокировка голосований снимается автоматически.

### 4.2 Загрузка реестра собственников

1. Председатель загружает файл со столбцами: номер помещения, ФИО, ИИН, площадь, вид собственности
2. Система показывает **превью с ошибками до применения**: несуществующие номера квартир, некорректные ИИН, дубликаты, расхождения площадей с уже введёнными
3. Председатель исправляет или подтверждает
4. При импорте **ИИН сразу хешируется** (HMAC-SHA256) — сам номер в базу не попадает

Реестр — **запасной** источник для верификации: основной — ГБД РН через Smart Bridge (§7). Реестр нужен, когда в ГБД РН нет записи (право не зарегистрировано, данные расходятся с нумерацией дома) или сервис недоступен. Загружать его необязательно, но без него такие случаи уходят на ручное подтверждение.

## 5. Flow: приглашение жильцов по ссылке

**Актор:** `CHAIRMAN` → `RESIDENT` · Основной путь

### 5.1 Создание ссылки

1. Председатель → «Жильцы» → «Пригласить»
2. Выбирает тип: **публичная ссылка для чата дома** или персональная
3. Задаёт срок (по умолчанию 14 дней) и при желании лимит активаций
4. Система показывает ссылку **один раз** — в базе хранится только её хеш
5. Председатель копирует и отправляет в общий чат жильцов ЖК

На экране управления ссылками председатель видит счётчик активаций и кнопку «Отозвать и выпустить новую» — на случай, если ссылка ушла за пределы чата.

### 5.2 Что происходит при переходе

Жилец открывает ссылку и видит **минимум**:

> **ЖК Асыл Арман, блок 3**
> Присоединиться как жилец
> [Продолжить]

Ни адреса, ни количества жильцов, ни финансов, ни фамилий. Ссылка лежит в чате, куда её мог переслать кто угодно, и до подтверждения личности о доме не сообщается ничего, кроме названия.

### 5.3 Регистрация

1. Ввод номера телефона → SMS с кодом → подтверждение
2. Ввод ФИО
3. **Выбор номера своего помещения** из списка помещений дома
4. Указание вида отношения: собственник или наниматель
5. Переход к верификации личности (§7)

Дом на этом шаге выбирать не нужно — он зашит в токен ссылки. Это и есть смысл приглашения: жилец сразу оказывается в нужной организации.

## 6. Flow: вступление без ссылки

**Актор:** `RESIDENT` → `CHAIRMAN` · Запасной путь

Для тех, кто не был в чате или потерял ссылку.

1. Жилец скачивает приложение и регистрируется по телефону
2. **Ищет свой дом по адресу** — поиск отдаёт только адрес и название, ничего больше
3. Указывает номер помещения, вид отношения и комментарий председателю
4. Создаётся `JoinRequest` в статусе `PENDING`
5. Председатель получает уведомление

**У председателя:**

```
Заявки на вступление                                    2

Асанов Данияр                                  кв. 45
+7 707 ••• •• 32 · собственник
«Купил квартиру в июне, прошу добавить»
Реестр: кв. 45 — Асанов Д.А. ✓ совпадение

[Подтвердить]  [Отклонить]
```

Система подсказывает результат сверки с реестром, но **решение принимает председатель**: реестр может быть устаревшим после недавней продажи квартиры.

6. При подтверждении создаётся `HouseMembership` и `UnitOwnership`; жилец получает уведомление и переходит к верификации личности

## 7. Flow: верификация личности и собственности

**Актор:** `RESIDENT` · Обязателен для права голоса

Ссылка-приглашение определила **дом**. Верификация определяет **личность** и **право собственности** — два разных факта из двух государственных источников:

| Что устанавливаем | Источник | Интерфейс |
|---|---|---|
| Кто этот человек: ИИН, ФИО | Digital ID (eGov) | `IdentityProvider` |
| Владеет ли он помещением в этом доме | ГБД «Регистр недвижимости» через Smart Bridge | `PropertyRegistryProvider` |

Путать их нельзя: иначе любой, кому переслали ссылку из чата, получил бы голос на собрании о расходовании денег дома.

**На этапе разработки оба провайдера — заглушки** (`MOCK`), поведение задаётся сид-данными. Подключение к Smart Bridge — отдельная задача, бизнес-логика от него не зависит.

### 7.1 Шаги

1. Жилец видит экран: «Подтвердите личность, чтобы участвовать в голосованиях»
2. Подтверждает согласие на получение сведений о его недвижимости из ГБД РН (версия текста согласия сохраняется)
3. Нажимает «Войти через eGov» → переход в Digital ID (веб — редирект, мобильное — системный браузер / eGov mobile)
4. Проходит идентификацию в eGov
5. Возвращается в приложение
6. **Сервер сам** обменивает одноразовый код на подтверждённые **ИИН и ФИО** у провайдера. ИИН сохраняется как `iin_encrypted` + `iin_hash`, выставляется `User.identity_verified_at`
7. **Сервер сам** запрашивает в ГБД РН объекты недвижимости по ИИН и ищет среди них помещение в этом доме

Шаги 6–7 устроены так намеренно: клиент ничего не сообщает о результате — только возвращается. Подделать верификацию перехватом одного HTTP-ответа нельзя.

Из ответа ГБД РН сохраняется только результат сопоставления (`VerificationSession.property_result`): найдено ли помещение, кадастровый номер, площадь, доля. Список остальной недвижимости жильца не сохраняется и не показывается никому — он не имеет отношения к дому.

### 7.2 Сопоставление

Помещение ищется по адресу дома (`House.cadastral_number` / `address_rka`, если заполнены, иначе нормализованный адрес) и номеру помещения.

| Результат | Что происходит |
|---|---|
| ГБД РН: помещение в этом доме найдено, совпадает с заявленным | `VERIFIED`, `verification_method = PROPERTY_REGISTRY`. Право голоса появляется сразу |
| ГБД РН: помещение в этом доме найдено, но другое | Привязка к помещению из ГБД РН + уведомление жильцу |
| ГБД РН: доля собственности < 1 | `VERIFIED` с долей; если собственников несколько — требуется выбрать представителя для голосования |
| ГБД РН: не найдено, загруженный реестр: ИИН и помещение совпали | `VERIFIED`, `verification_method = OWNER_REGISTRY_MATCH` |
| Не найдено нигде | `PENDING` → очередь на ручное подтверждение председателю |
| ГБД РН недоступна | Сверка с загруженным реестром; если нет совпадения — `PENDING` с повторной автоматической проверкой в течение 24 часов |
| Заявлен наниматель (`TENANT`) | Запрос в ГБД РН не выполняется. Личность подтверждена, `VERIFIED` как наниматель, без права голоса |

«Не найдено» — не отказ. Право могло быть ещё не зарегистрировано после покупки, помещение могло перейти по наследству. Такие случаи решает председатель, который знает своих жильцов.

### 7.3 Что даёт верификация

| Действие | Без верификации | С верификацией |
|---|---|---|
| Просмотр объявлений и бюджета дома | да | да |
| Создание заявок | да | да |
| Просмотр своих начислений и оплата | да | да |
| **Голосование** | **нет** | да (только собственник) |
| **Подписание документов ЭЦП** | **нет** | да |

При подписании бюллетеня ИИН из сертификата ЭЦП сверяется с ИИН, подтверждённым Digital ID. Это закрывает случай, когда человек верифицировался сам, а подписать пытается чужой ЭЦП.

## 8. Flow: добавление работников

**Актор:** `CHAIRMAN`

1. Председатель → «Персонал» → «Добавить»
2. Заполняет ФИО, должность, специализации, рабочий телефон, график, фото
3. Отмечает **«Виден жильцам»** — прямое требование прозрачности: жильцы должны знать, кто работает в их доме
4. Если работнику нужен вход — указывает телефон и отправляет персональное приглашение
5. Работник регистрируется по телефону с OTP; Digital ID и ЭЦП ему не нужны — он не голосует и не подписывает документы

### 8.1 Добавление бухгалтера

**Актор:** `CHAIRMAN` → `ACCOUNTANT`

1. Председатель → «Персонал» → «Добавить бухгалтера» → почта и ФИО
2. Step-up: председатель подтверждает действие TOTP
3. Создаётся `User` в статусе `PENDING` (или используется существующий по почте) и `HouseMembership` с ролью `ACCOUNTANT`, `joined_via = CHAIRMAN_ADD`
4. На почту — ссылка установки пароля (72 часа), затем обязательная 2FA
5. Для подписания отчёта бухгалтер проходит Digital ID — ИИН подписанта сверяется с подтверждённым

Эндпоинт: `POST /houses/:id/members`. Отзыв — `DELETE /houses/:id/members/:userId`, с записью в аудит и уведомлением председателю.

Что видят жильцы в справочнике персонала: ФИО, должность, фото, рабочий телефон, график. Чего не видят: зарплату, личный телефон, паспортные данные, домашний адрес.

## 9. Состояния дома

```
CREATED ──────► UNITS_GENERATED ──────► CHAIRMAN_ACTIVE
                                              │
                                              ▼
                                     AREAS_COMPLETE
                                     (is_voting_ready = true)
                                              │
                                              ▼
                                        OPERATIONAL
```

| Состояние | Что доступно |
|---|---|
| `CREATED` | Только админ платформы |
| `UNITS_GENERATED` | Можно назначить председателя |
| `CHAIRMAN_ACTIVE` | Заявки, объявления, персонал, финансы, приглашения жильцов |
| `AREAS_COMPLETE` | Дополнительно: голосования |
| `OPERATIONAL` | Всё, включая отчётность |

Заявки и финансы работают до заполнения площадей намеренно: председателю нужно начать пользоваться системой сразу, а не после недели ввода данных. Блокируется только то, что без площадей юридически некорректно, — голосования.

## 10. Обработка ошибочных ситуаций

| Ситуация | Поведение |
|---|---|
| Двое заявляют одно помещение | Оба попадают в `PENDING`, председатель решает. Автоматически не разрешается — это может быть развод, наследство или мошенничество |
